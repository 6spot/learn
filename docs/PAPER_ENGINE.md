# 纸张模板与统一排版引擎

> 状态：核心技术设计草案；未运行 PoC。本文首先规定边界与要验证的问题，不假定所有模板都有相同的 Word 编辑能力。

## 1. 目标

给定同一份纸张描述，输出稳定、可打印的几何布局，再通过 Canvas、PDF、DOCX 三种方式表达。模板决定纸张格线与选项；内容决定填什么；布局层决定坐标、占格、换行与分页；渲染层只负责呈现。

```text
PaperDocument
  ├── pageSpec                 纸张与边距
  ├── templateId/version       模板和版本
  ├── templateOptions          格子线型、大小与颜色
  └── content                  空白 / 填字 / 描红 + 文字
           │
           ▼
      validate + layout
           │
           ▼
      LayoutPages
           ├── 页面物理尺寸
           ├── 格线/路径集合
           ├── 字形坐标与占格映射
           └── 分页和块结构
              │
       ┌──────┼────────┐
       ▼      ▼        ▼
     Canvas  PDF      DOCX
```

## 2. 输入与输出契约（提议）

**输入** `PaperDocument`：
- `templateId` 和 `templateVersion`：标识确定版本的模板定义；
- `pageSpec`：A4/A5 等尺寸、横/竖、各边距与整页铺格选项；
- `templateOptions`：格宽/高、格间距、线型、辅助虚线、线颜色与粗细；
- `content.mode`：`blank | filled | tracing`；
- `content.title` 与 `content.paragraphs`：真实逻辑段落，而不是原始 Word 硬换行。

**输出** `LayoutPages`：按页包含可定位的线段/路径/网格/文字对象和物理尺寸、分页信息、文本单元到格子的映射。建议坐标统一用**毫米**，各渲染器在边界转换为 Canvas 像素、PDF pt、Word twip 等目标单位；毫米是建议而非已最终确认的协议。

无论 PDF、DOCX、预览，布局规则的决策只执行一次；不同渲染器允许因字体与目标文档模型差异存在有限的偏差，需通过验收标准界定。

## 3. 模板和内容分离

| 模板/模式 | 格线结构 | 内容行为 |
|---|---|---|
| 作文方格 | 正方形整页格线 | 标题居中、正文按格、自然换行、段首空两格 |
| 田字格 | 正方形外边框 + 中心横/竖辅助线 | 空白、填字、描红 |
| 米字格 | 田字格 + 两条对角辅助线 | 空白、填字、描红 |
| 拼音四线三格 | 四线三格横线组 | 拼音/空白；字符位置需另行定义 |
| 组合及其他格 | 由多个格线区域组合 | 按对应内容区域和能力展示选项 |

这些只是格线和内容布局策略的关系，不能把拼音线强行伪装成汉字方格。模板公开自身支持的内容模式与导出能力；不支持的设置不显示。

模板定义建议是代码中的声明式数据，初期不需要数据库模板 CMS。未来确需远程动态开关时，才把可配置项放入云端。

## 4. 作文格的已讨论规则

基于两篇实际作文 Word 的转换经验，第一版作文格必须满足：

1. 标题在方格行中居中；标题和正文可空一整行。
2. 整页铺满方格；未使用区域仍然显示格线。
3. 只按实际逻辑段落分段；原 Word 因排版造成的硬换行不应成为新段落。
4. 每段开始空两格，之后自然填满并换行。
5. 汉字、数字和中文标点的占格规则要明确；默认中文标点占独立格。
6. 不因正文长度而改变已选择纸张格子的物理尺寸与整页布局。
7. 多页保持一致的版式与页边距。

文字处理需要特别测试：中文引号/括号/句号的禁则、连续数字、英文单词、空格、全角/半角、拼音声调、表情及 Unicode 组合字符。**不能用 `str[i]` 直接将 UTF-16 代码单元当作完整文字。** 英文单词怎样分格、标点禁则的优先级仍属待决。

## 5. 三种渲染输出

### Canvas：小程序预览

在微信本地根据 `LayoutPages` 绘制，尺寸随屏幕缩放但仍保留纸张真实宽高比。放大/缩小只影响展示视口。预览不需要走云函数，也不扣次数。

### PDF：打印几何基准

在 CloudBase 云函数中将同一布局转换为 PDF 纸张尺寸、格线、文字。需验证中文字体的版权授权、云端嵌入/子集、字形缺失、文件大小及微信预览能力。以实际 A4 打印为基准，不能仅看手机缩略图。

### DOCX：可编辑输出

通过文档表格、边框、段落等 **真实 Word 对象** 表达。初期可考虑 JS/TS `docx` 库，但必须测 WPS 与 Microsoft Word 的换页、行高、边框和表格编辑能力。

对于米字格斜线、拼音格等复杂模板，不能保证原生 Word 结构均能精确表达；模板应有显式 DOCX 能力标记。未通过验证的模板只提供 PDF，**不能以整页截图假装 Word 可编辑**。

## 6. 正确性与一致性

不要求跨渲染器像素级一致；需要：
- A4 等物理尺寸正确，打印为 100% 比例时格宽及边距符合公差；
- 页数、行列位置、正文占格和分页符合规范；
- PDF/Word 的适用能力和限制向用户真实呈现；
- 所有调整能复用同一套测试样本，避免“改作文格影响米字格”。

初步公差及样张尺寸将在 PoC 期间确定，不能凭空规定毫米级指标却不实测。

## 7. 技术验证顺序（下一轮讨论重点）

1. 定义首批纸张和默认物理格宽、边距、分页。
2. 确定文本占格、标点、空格、英文和段落的规则。
3. 做 A4 整页作文格两页样张，与原始两篇作文效果对照。
4. 做田字格、米字格、拼音格 PDF 样张，检查辅助线/虚线。
5. 验证 DOCX 在 WPS/Word 的真实编辑能力；根据结果标注各模板支持情况。
6. 确定测试向量、字体方案，再连接微信预览与云函数。
